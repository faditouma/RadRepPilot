# Textbook workflow coverage

Internal development document. This file maps the private content reference to implementation work. Chapter and source information in this document must never be passed to user-visible workflow content, report text, navigation, accessibility labels, help text, or provenance panels.

## Assessment method

Coverage was assessed against:

- the actual fields and defaults in `src/data/reportingWorkflowSchemas.ts`;
- report generation in `src/utils/reportGenerators.ts` and the legacy generators it calls;
- completeness branches in `src/utils/qualityMetrics.ts`;
- implemented, partial, and planned entries in `src/data/moduleNavigationTree.ts`;
- classification previews in `src/radrep/calculatorRegistry.ts` and `src/data/radsSystemsRegistry.ts`;
- incidental helpers in `src/data/incidentalFindingsRegistry.ts`;
- shared active-draft serialization in `src/lib/workflowDraftStorage.ts`.

A navigation placeholder, incidental helper, or classification preview is not counted as a complete reporting workflow. A complete workflow must have structured fields, findings and impression generation, completeness scoring, draft compatibility, navigation, responsive rendering, tests, and internal metadata.

## Consolidation and non-duplication decisions

1. Chapters 31 and 38 will share typed pulmonary-nodule field groups, but incidental-nodule and screening workflows remain separate because eligibility, category logic, and recommendations differ.
2. Chapters 32 and 35 remain separate workflows. They can share CTPA technical-quality and right-heart field groups, but pulmonary-embolism exclusion and pulmonary-hypertension etiologic assessment are different clinical tasks.
3. Chapters 39 and 40 remain separate modality-specific workflows under a shared adaptable viral-pneumonia content family. Both retain COVID-specific options and internal historical flags.
4. Chapters 12–14 remain separate cancer-staging workflows; shared pelvic MRI context and nodal/distant-disease field groups may be reused.
5. Chapters 28–30 remain separate transplant workflows because recipient Doppler surveillance and donor surgical planning have different users and measurement requirements.
6. Chapters 50 and 51 remain separate postprocedural and preprocedural AAA workflows; shared aortic measurement primitives may be reused.
7. Chapter 10 uses one HCC workflow with separate LI-RADS and OPTN classification engines because the observation dataset overlaps but category purposes differ.
8. Chapter 26 uses one pancreatitis workflow with acute, chronic, and acute-on-chronic modes because those modes share anatomy while requiring conditional terminology and complication fields.
9. No chapter is currently classified as `not_suitable_as_standalone_module`.

## Architecture plan guided by chapters 1–4

The expansion will preserve the current schema renderer and workflow identity while moving definitions out of the single large schema file incrementally:

1. Keep `reportingWorkflowSchemas` as the stable public export so existing navigation and saved draft `moduleId`/`moduleType` values remain compatible.
2. Extract shared, nonclinical primitives first: comparison fields, technical-quality fields, four-state findings, measurements, overrides, and communication documentation.
3. Add clinical-section schema files only as their first module is implemented:
   - `src/data/reporting/cancerImaging.ts`
   - `src/data/reporting/abdominalPelvic.ts`
   - `src/data/reporting/thoracic.ts`
   - `src/data/reporting/neuroradiology.ts`
   - `src/data/reporting/cardiovascular.ts`
4. Keep module-specific generator functions in matching clinical-section files or narrowly scoped generator modules. Do not create one universal disease generator.
5. Keep classification engines separate from report prose, versioned, and disabled for automatic categories until primary-source verification and boundary tests are complete.
6. Continue using the existing active-draft storage key and payload shape. New schemas must restore drafts by stable `moduleId` and `moduleType`.
7. Require blank-safe defaults for clinically meaningful states, fast explicit negative templates, conditional fields, technical-limit propagation, manual overrides, and concise synthesis.
8. Keep internal source/review metadata non-rendered. Automated tests must reject private-reference identifiers from visible schema strings, navigation, and generated reports.
9. Add loadability and draft-compatibility regression tests whenever the schema registry is split.
